# Деплой бота

Бот работает на хостинге [bothost.ru](https://bothost.ru) в Docker-контейнере. Хостинг сам собирает бота из этого репозитория по `Dockerfile` в корне и перезапускает при падении. Новую версию из ветки деплоя (`main`) хостинг подтягивает по кнопке «Обновить из git».

## Как это устроено

`Dockerfile` собирает бота в два этапа:

1. **Сборка** — образ `maven:3.9-eclipse-temurin-21`. Команда `mvn -B package -pl bot -am -DskipTests` собирает модуль `bot` вместе с `common` в один jar со всеми зависимостями (`bot/target/freedom-bot.jar`). Тесты пропускаются: они уже прошли в CI перед слиянием в `main`.
2. **Запуск** — образ `eclipse-temurin:21-jre`, в нём только Java и готовый jar. Jar лежит в `/opt/freedom-bot`, а не в `/app`: в `/app` хостинг монтирует исходники из Git.

Токен в репозиторий не попадает: хостинг передаёт его в контейнер переменной окружения `BOT_TOKEN`, которую читает `BotConfig`.

## Деплой с нуля

1. Получить токен бота у [@BotFather](https://t.me/BotFather).
2. На bothost.ru создать бота:
    - **Платформа:** Telegram.
    - **Язык разработки:** любой (например, Python). Java в списке нет, а с собственным Dockerfile язык не используется.
    - **Bot Token:** токен бота.
    - **Локация:** Нидерланды (Амстердам).
    - **Git URL репозитория:** `https://github.com/FreedomMinecraft/freedom-bot.git` (с `.git` на конце, иначе форма не принимает ссылку).
    - **Ветка:** `main`.
    - **Дополнительные настройки:**
        - «Использовать собственный Dockerfile» — **включить**;
        - «Использовать домен» — выключить: бот работает через long polling, веб-доступ ему не нужен;
        - «Главный файл» — оставить пустым.
3. Нажать «Создать бота» и дождаться сборки. В логах сборки должны быть `BUILD SUCCESS` и `Build completed`, в логах работы — `Бот запущен.`
4. В переменных окружения бота добавить `DB_URL=jdbc:sqlite:/app/data/bot.db` — база подписок — и перезапустить бота. На bothost между обновлениями сохраняется только папка `/app/data` (подробнее — [storage.md](storage.md)). Без `DB_URL` бот работает, но подписки пропадают при каждом перезапуске.
5. Проверить: написать боту `/ping`, ответ — `pong`. В логах работы — строка `Подписки хранятся в базе: jdbc:sqlite:/app/data/bot.db`, в файловом менеджере bothost в папке `data` — файл `bot.db`.

## Обновление

1. Влить PR в `main`.
2. В панели бота на bothost нажать «Обновить из git»: хостинг пересоберёт и перезапустит бота. Сам после push он этого не делает.
3. Проверить по логам и командой `/ping`.

## Состав сервера без пересборки

Состав (`/admins`, `/eventors`, `/media`), чаты и ссылки поддержки бот читает при запуске. Откуда — решает переменная окружения `SERVER_INFO_FILE`:

- **не задана** — файл `server-info.json`, вшитый в jar (`bot/src/main/resources`). Менять его — через PR и «Обновить из git»;
- **задана** — файл по этому пути. На bothost: `SERVER_INFO_FILE=/app/data/server-info.json`. Файл правится в файловом менеджере bothost, коммиты не нужны.

Первая настройка:

1. Скачать `bot/src/main/resources/server-info.json` из репозитория и загрузить в папку `data` через файловый менеджер bothost.
2. В переменных окружения бота добавить `SERVER_INFO_FILE=/app/data/server-info.json` и перезапустить бота.
3. В логах работы — строка `Данные о сервере: файл /app/data/server-info.json`.

Смена состава: отредактировать `data/server-info.json` в файловом менеджере → перезапустить бота → проверить `/admins` или `/media`.

Файл в репозитории остаётся запасным вариантом и образцом формата, на нём же проверяется CI. Файл в `/app/data` CI не проверяет: если в нём ошибка, бот не запустится, а причина будет в первых строках логов работы. Быстро вернуть бота — удалить переменную `SERVER_INFO_FILE` и перезапустить: бот возьмёт данные из jar.

## Важно

- **Один токен — одна запущенная копия.** Пока бот работает на хостинге, запускать его локально с тем же токеном нельзя: Telegram вернёт 409 Conflict. Для разработки нужен отдельный тестовый бот со своим токеном в Run Configuration.
- Время в логах — UTC.
- Предупреждения `overlapping resource` от `maven-shade-plugin` в логе сборки безвредны: это одноимённые файлы лицензий и манифестов в разных библиотеках.

## Если что-то сломалось

- **Сборка упала** — смотреть логи сборки (вывод Maven и Docker).
- **Сборка прошла, а бот не отвечает** — смотреть логи работы. Ошибка `Не задан токен бота` означает, что не указан токен в настройках бота на хостинге.
- **Статус `restarting`** — процесс падает при запуске; причина — в первых строках логов работы.
- **`Не найден файл с данными о сервере`** или **`Не удалось прочитать данные о сервере`** — нет файла по пути из `SERVER_INFO_FILE` или в нём ошибка JSON (лишняя/пропущенная запятая, кавычка, опечатка в ключе). См. «Состав сервера без пересборки».
